Differences from ElastAlert 2
*****************************

ElastAlert 3 reads existing ElastAlert 2 ``config.yaml`` and rule files unchanged and writes the same writeback
documents. Alert text, silence keys, realert timing, the queried time range (``gt start``, ``lte end``) and the rule
type math match ElastAlert 2. This page lists what is new, what behaves differently on purpose, and what is not
supported. Elsewhere in this documentation, the same points are marked with a red **ElastAlert 3** note.

How compatibility is checked
============================

The same deterministic data set (3,000 documents) is replayed through Python ElastAlert 2.31.0 and ElastAlert 3
with ``--debug``, and the alerts are compared: 37 rules covering every supported rule type and many options give
**931 alerts, identical**. EQL, ES|QL, Kibana / OpenSearch Discover links and ``TimeEnhancement`` give **203 alerts,
identical**. Summary tables and Discover URLs generated by ElastAlert 2 are compared byte for byte in the unit tests.

Tested against Elasticsearch 7.17 and 8.15 and OpenSearch 2.17, single node.

**Not tested**: TLS and client certificates, basic auth / API key / bearer against a secured cluster, ``unix`` /
``unix_ms`` timestamps, ``sync_bucket_interval`` / ``allow_buffer_time_overlap``, degraded clusters, multi-node
clusters, Windows and macOS.

New in ElastAlert 3
===================

- The :ref:`correlation <correlation>` rule type: events of several searches (leaves) on the same pivot within a
  window, combined with ``AND``, ``OR``, ``THEN`` and ``NOT``.
- The :ref:`geo_velocity <geo_velocity>` rule type: an event too far from the previous one of the same ``query_key``
  for the time between them (impossible travel).
- The :ref:`beacon <beacon>` rule type: the events of a ``query_key`` value at regular intervals (C2 beaconing).
- The :ref:`baseline <baseline>` rule type: the event count of a bucket against the same buckets of the history (seasonal
  z-score or MAD).
- The :ref:`outlier <outlier>` rule type: an entity whose metric is far above the median of its peers (``query_key`` values), optionally within a group (``peer_field``).
- The :ref:`risk <risk>` rule type and the ``risk_score`` / ``risk_objects`` options: behavioural alerts when the alerts of an entity (host, user) add up to a risk limit.
- ``max_occurrences`` of the :ref:`new_term <new_term>` rule type: alert on a term seen at most that many times in the history
  ("rare"), not only on a never-seen one.
- :ref:`active_hours <active_hours>`: ignore matches outside time windows, in a given time zone.
- :ref:`mitre_attack <mitre_attack>`: the ATT&CK techniques of a rule, checked at load, written to the alert documents,
  added as TheHive / IRIS tags, and exported as an ATT&CK Navigator layer by the ``mitre-layer`` subcommand.
- :ref:`Sigma rules <sigma>`: ``sigma: <file>`` compiles a Sigma detection into the rule's ``filter``, with built-in and custom field-mapping pipelines, ``sigma_folders`` to run plain Sigma files, Sigma correlation rules and filters, and the ``sigma-convert`` subcommand.
- :ref:`ingest_timestamp_field <ingest_timestamp_field>`: query on the ingest time, so late documents are found
  exactly once.
- :ref:`filter_terms_file <filter_terms_file>`: a ``terms`` filter from a list of indicators in a file, reloaded when the file changes.
- :ref:`exceptions <exceptions>`: named documents a rule ignores (a Sigma selection or a Query DSL query, optional ``reason`` and ``expires``), excluded in the query.
- :ref:`read_doc_values <read_doc_values>`: read the timestamp and the ``query_key`` from doc values instead of ``_source``.
- :ref:`split_on_limit <split_on_limit>`: read every result of an EQL / ES|QL range that fills ``max_query_size``.
- :ref:`search_timeout, terminate_after, preference and routing <search_options>`.
- :ref:`fetch_full_source <fetch_full_source>` and ``use_pit`` (see :ref:`ea3_config`).
- Prometheus: :doc:`rule lag, last success time and Elasticsearch request durations <recipes/exposing_rule_metrics>`.
- The ``rust.add_field``, ``rust.drop_if`` and ``rust.lookup`` :doc:`match enhancements <enhancements>`.
- The ``validate`` subcommand (``validate --es`` checks the filters and fields against the mappings), and ``--es_debug_trace`` with responses.
- Hot reload keeps the state of a changed rule; pending alerts and aggregation groups survive restarts.

A rule using ``correlation``, ``geo_velocity``, ``beacon``, ``baseline``, ``outlier``, ``risk``, ``risk_score``, ``max_occurrences`` on ``new_term`` or a ``rust.*`` enhancement does not load in ElastAlert 2. ElastAlert 2 ignores
``active_hours``, ``mitre_attack``, ``sigma``, ``sigma_folders``, ``ingest_timestamp_field``, ``fetch_full_source``, ``search_timeout``, ``terminate_after``, ``preference``, ``routing``, ``split_on_limit``, ``read_doc_values``, ``filter_terms_file`` and ``exceptions``.

Behaviour differences
=====================

.. list-table::
   :header-rows: 1
   :widths: 20 35 45

   * - Topic
     - ElastAlert 2
     - ElastAlert 3
   * - Documents fetched
     - whole ``_source`` for every hit
     - only the fields the rule type uses; the full document is fetched (``_mget``) for the few matches. Same alert text. Set ``fetch_full_source: true`` or ``include:`` to opt out
   * - Failed alerter
     - the whole alert is marked unsent and every alerter is resent
     - per-alerter status in ``alerters_sent`` (``slack``, then ``slack#2``, ... for the same alerter used twice); only failed alerters are retried (30 s doubling, max 1 h, until ``alert_time_limit``)
   * - Writeback
     - one request per document
     - one ``_bulk`` per second (or 500 docs); client-side ids make retries idempotent
   * - Pending alerts
     - polled every ``run_every``, one ``delete_by_query`` each
     - kept in memory, mirrored in Elasticsearch, aggregation groups sent by a timer
   * - Paging
     - scroll, recursive, capped at 990 pages
     - point in time + ``search_after``, iterative, no cap; a plain search first, the point in time is opened only when the page is full
   * - ``new_term`` startup
     - one terms aggregation per day of ``terms_window_size``
     - one composite aggregation; ``window_step_size`` is ignored
   * - ``change`` rule
     - state shared by all change rules (a bug)
     - state per rule
   * - Shutdown
     - ``SIGINT`` exits immediately
     - running rules finish, writeback is flushed (10 s limit)
   * - Replay with ``--end``
     - open aggregation groups are sent only if their time arrives
     - open groups are sent at the end
   * - ``silence``
     - checked in Elasticsearch per match
     - held in memory, refreshed every ``run_every`` (a silence set from the command line takes up to one ``run_every`` to apply)
   * - Resume right after a write
     - n/a
     - status documents are visible to search after the next refresh (about 1 s); a restart within that second resumes from ``end - buffer_time``
   * - Match timestamps
     - keep the original offset
     - printed as UTC ``Z``
   * - ``spike_aggregation`` with an empty bucket
     - the rule run fails with a ``TypeError``
     - the value is skipped
   * - Log lines
     - ``INFO:elastalert:...`` per call
     - same text; the two lines of a debug alert are emitted in one call so parallel rules do not interleave them
   * - Concurrency
     - thread pool
     - one task per rule, ``max_threads`` limits concurrent runs
   * - Disabled rules log
     - printed every cycle
     - printed only when some exist
   * - EQL sequence / join queries
     - no events, silently
     - the run fails with an error (only event queries work); use the ``correlation`` rule type instead
   * - EQL ``timestamp_field``
     - always the Elasticsearch default ``@timestamp``
     - the rule's ``timestamp_field`` is sent when it is not ``@timestamp``
   * - Discover link that cannot be built (bad ``kibana_url``, shortener unreachable)
     - the rule run fails and the alert is not sent
     - an error is logged and the alert goes out without the link
   * - Discover filters
     - ``meta.value`` keeps the key order of the YAML
     - keys are sorted (display text of the filter pill only)
   * - ``TimeEnhancement`` with ``frequency``, ``spike``, ``flatline``, ``cardinality``
     - the time range sentence is built from the rewritten ``@timestamp``, with a host-dependent time zone
     - the sentence is left out
   * - Error notification mails
     - ``SMTP(smtp_host)`` only; generic error mails have an empty body
     - ``smtp_port``, TLS and login are honoured; generic error mails carry the message
   * - Removing a rule file
     - the rule keeps running until it is disabled
     - the rule stops at the next reload

Not supported
=============

A rule or a configuration that needs one of these is **rejected at load** with a message, unless marked "ignored".

- Python plugins of any kind: rule types, alerters, rule loaders, match enhancements, ``jinja_filters``. See
  :doc:`extending`.
- Per-rule Elasticsearch connections (``es_host`` and connection options in a rule that differ from ``config.yaml``).
- AWS SigV4 signing of Elasticsearch requests (``aws_region``, ``profile``): Amazon OpenSearch Service with IAM
  authentication cannot be queried. The SNS, SQS and SES alerters sign their own requests.
- ``notify_alert`` (ignored; use ``notify_email``), statsd (ignored), ``replace_dots_in_field_names``, the Python
  ``logging:`` section (ignored).
- ``include_rule_params_in_matches``, ``_source_enabled: false``, ``summary_table_type: html``.
- ``aggregation_alert_time_compared_with_timestamp_field`` (ignored).
- Email: ``email_image_keys`` / ``assets_dir`` inline images, ``smtp_cert_file`` / ``smtp_key_file``. PagerDuty: NTLM
  proxy authentication.
- Helm chart. Elasticsearch older than 7.
- High availability: do not run two instances against the same writeback index, they would alert twice (same as two
  ElastAlert 2 instances).

Options accepted and ignored: ``es_send_get_body_as``, ``ssl_show_warn``, ``misfire_grace_time``,
``max_aggregation``.

Performance
===========

Measured on one machine (24 threads, 30 GB; Elasticsearch 8.15.5 single node with a 2 GB heap in Docker, same host for
both programs). These are not a benchmark suite; your data and hardware will differ.

.. list-table::
   :header-rows: 1
   :widths: 40 30 30

   * - Scenario
     - ElastAlert 2.31.0
     - ElastAlert 3
   * - Frequency rule over 400,000 documents (1.3 KB each), 3 days, 6 h ``buffer_time``
     - 34.0 s, 389 MB max RSS
     - 3.0 s, 145 MB max RSS, about 11 times faster
   * - Same, hits / matches
     - 398,769 / 549
     - 398,769 / 549, every match body identical
   * - Daemon with 500 rules, 35 s after start
     - 89 MB, every rule had run once
     - 38 MB, every rule had run once

The difference comes from a compiled runtime without a global interpreter lock, field projection (only the timestamp
and key fields are read from Elasticsearch), bulk writeback and compact event windows.

:ref:`correlation <correlation>` rules have no ElastAlert 2 counterpart. Same machine and the same 400,000 documents
over 3 days (6 h ``buffer_time``, ``--debug``, ``query_key: user.name``, median of 3 runs; rules in
``bench/rules-corr``). The leaves reading the same index share one search and only the pivot and the timestamp are
read; the whole documents are fetched for the matches only, so the memory grows with the matches held until the end of
the run, each with the documents of its leaves.

.. list-table::
   :header-rows: 1
   :widths: 52 16 16 16

   * - ``correlation_query`` (``timeframe``)
     - Time
     - Max RSS
     - Matches
   * - ``fail THEN ok``, 5 failures (15 min)
     - 4.6 s
     - 313 MB
     - 3,767
   * - ``fail AND denied``, 3 and 2 events (10 min)
     - 3.3 s
     - 307 MB
     - 4,172
   * - ``unauth THEN NOT db`` (10 min)
     - 3.6 s
     - 342 MB
     - 7,557
   * - ``(fail OR denied) THEN ok THEN (web2 AND db)`` (20 min)
     - 7.7 s
     - 1,908 MB
     - 15,995
   * - ``fail AND web1 AND NOT denied`` (10 min)
     - 4.8 s
     - 219 MB
     - 2,300

The first three rules written with the ``correlation_steps`` of ElastAlert 3.2.0 take the same time (within 3 %).

Migrating from ElastAlert 2
===========================

1. Run ``elastalert --config config.yaml validate`` on your existing configuration and rules folder. Every rule that
   uses something ElastAlert 3 cannot do is reported with the reason.
2. Point ElastAlert 3 at a copy of the writeback index (``create-index --index elastalert3_status --old-index
   elastalert_status``), or at a new one, and run it next to ElastAlert 2 with ``--debug``. Compare the alerts in the
   logs.
3. Stop ElastAlert 2, then run ElastAlert 3 on the real writeback index: it resumes where ElastAlert 2 stopped, and
   picks up unsent alerts and open aggregation groups.
4. Scripts that parse ``elastalert-test-rule`` output need adjusting: the ``test-rule`` text is similar, not
   identical.
